Deploying the RSVP site

A test deployment on a real public URL — enough to see the WhatsApp preview card, which cannot be tested any other way.

Why this is needed at all: WhatsApp builds its link preview by fetching the page from its own servers. It can reach neither localhost nor 192.168.68.114, so the card is invisible until the site has a public address. Everything else already works locally.

1Before you push

The repository is github.com/DmitriPer/weddingRsvp, branch main. Local main is 3 commits ahead of GitHub, plus the settings-tab work that is still uncommitted.

Look at /admin/settings first — the 24-hour time selects, the collapsible templates and the taller text boxes are the part nobody has reviewed. Then:

npm run build          # must pass; this is the check Vercel will run
git add -A
git commit -m "24-hour time selects, collapsible templates"
git push origin main

Never commit .env.local. It holds the secret key. .gitignore covers .env.local and .env.*.local — but not .env.local.bak, which is the obvious name for a backup and the one spelling that is not ignored. If you want a copy, put it outside the repository.

2Create the Vercel project

  1. Sign in at vercel.com with the GitHub account that owns the repo.
  2. Add New → Project, then import DmitriPer/weddingRsvp.
  3. Framework preset detects Next.js. Leave build command, output directory and install command exactly as they come — this project needs no custom build settings.
  4. Confirm the production branch is main. The old branch is the abandoned first attempt and must never be deployed.
  5. Do not deploy yet — add the environment variables first (next step). A deploy without them fails at build time, when the Supabase client finds no URL.

3Environment variables

Add these four under Settings → Environment Variables, ticking Production, Preview and Development. Copy the values from your local .env.local.

NameValueNotes
NEXT_PUBLIC_SUPABASE_URL same as local Public. Same Supabase project as your local dev.
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY same as local Public by design. Every table is RLS deny all, so this key alone reads nothing.
SUPABASE_SECRET_KEY same as local Server-only. Never rename it with a NEXT_PUBLIC_ prefix — that prefix means "ship this to the browser", which would open the whole database to anyone who views source.
NEXT_PUBLIC_SITE_URL leave it for now You do not know the URL until the first deploy finishes. Step 4 handles it.

Do not add ADMIN_EMAIL or ADMIN_PASSWORD. They exist only for the one-off scripts/create-admin.ts, which has already run. The app never reads them, and putting a password in a hosting dashboard for no reason is how it leaks.

4Deploy, then fix the site URL, then deploy again

This is the one genuinely awkward step, and it is unavoidable: the app needs to know its own address, and the address is assigned by the first deploy.

  1. Deploy. It will succeed, and it will be wrong — every invite link and the preview image URL will still point at 192.168.68.114.
  2. Copy the URL Vercel assigns, e.g. wedding-rsvp-xxxx.vercel.app.
  3. Set NEXT_PUBLIC_SITE_URL to it, with https:// and no trailing slash.
  4. Redeploy. Saving the variable is not enough.

Why saving isn't enough. Anything named NEXT_PUBLIC_* is baked into the JavaScript at build time, not read at runtime. Until a new build runs, the old value is still compiled into the deployed files. In Vercel: Deployments → ⋯ → Redeploy.

One variable feeds three separate things, so they break and fix together: the guest invite links, the admin copy-link button, and the absolute og:image URL in the WhatsApp card.

5Supabase

Nothing has to change — the deployed site talks to the same project your local dev does, and the admin account you created already works there. Two optional bits of hygiene:

  • Auth → URL Configuration → Site URL: set it to the Vercel URL. Password sign-in does not need it, but any future email flow (password reset) would send links to the wrong place without it.
  • Keep the test data. The database holds two invented invites. Real guests go in only when you say so.

6Check it worked

  • Open the site root — the landing page shows the artwork, no guest data.
  • Sign in at /admin with your existing credentials.
  • Copy a guest's invite link from the invitee table. Confirm it starts with the Vercel URL, not the LAN address.
  • Open that link: the greeting names the guest, the sheet opens, an RSVP saves, and the status moves to submitted in the admin table.
  • Check ניווט opens Waze at the venue and יומן downloads an .ics with the right date and 24-hour time.
  • Send yourself the invite link on WhatsApp. The card should show the florals, the monogram, ניקול ודימה, the date and the venue.

WhatsApp caches previews per URL, hard. The first time a link is fetched, that card is stored for a long time. If it looks wrong and you fix it, re-sending the same link shows you the old card and you will chase a bug you already fixed. Test the fix with a different URL — add &x=2 to the link, which the app ignores.

To inspect the tags directly, paste the URL into Facebook's sharing debugger (developers.facebook.com/tools/debug). It reads the same OpenGraph tags and will re-scrape on demand.

7Before real invitations go out

A .vercel.app address is fine for testing and wrong for a wedding. Everything below has to be true first — and note that each guest's WhatsApp caches the card against whatever URL you sent them, so changing domains after sending means the old preview lingers.

  • Real domain attached in Vercel, and NEXT_PUBLIC_SITE_URL changed to it, followed by a redeploy.
  • Ceremony time confirmed. It is what lands in every guest's calendar.
  • Rebuild the preview card if any of the names, date or venue changed since it was last built: npm run og-card, then commit and push. The card is a file, not a page — it does not follow the settings tab, and every screen in the app will look correct while the card is stale.
  • Real guest list imported, replacing the test rows.
  • Contact phone set — it is what the past-deadline screen tells people to call.

8If something breaks

Vercel keeps every previous deployment. Deployments → pick the last good one → Promote to Production puts the old build back in seconds; no git revert needed.

Build failures show the full log under the deployment. The usual causes here, in order: a missing environment variable, or a TypeScript error that npm run build would have caught locally — which is exactly why step 1 runs it first.
