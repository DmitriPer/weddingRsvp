01 The two journeys

Everything in this app happens inside one of two separate journeys, and they never overlap. A guest never sees a login screen. An admin never sees the RSVP form.

Guest journey — no login, ever

1

Guest gets a personal link

Every invite has its own secret code baked into the URL — that code is the guest's password. No account, no login screen for guests, ever.

2

They open it

The app quietly notes "this invite has been opened" the first time — unless it detects the visit came from a bot (link-preview crawlers, WhatsApp's own preview fetcher), so a shared preview card doesn't falsely mark it opened.

3

They answer: coming or not?

A short form: attending or not, how many adults, how many kids.

4

Their answer is saved twice

Once as "their current answer" (overwritten if they change it later), and once as a permanent line in a history log that's never erased — so a change of heart is visible, not lost.

5

If they come back

Same link shows their previous answer pre-filled, ready to edit. Submitting again is recorded as a correction, not a fresh answer.

Admin journey — behind a login

1

Log in at a private page

Nothing under the admin area loads until you're signed in — you're bounced to the login screen first.

2

See everyone at a glance

Every guest, their status, their current answer if they've given one.

3

Manage the guest list

Add a guest by hand, delete one, or upload a spreadsheet to add a whole batch at once.

4

Read every answer, and its history

Open any guest to see their current RSVP plus every previous version of it.

5

Check the running totals

How many pending, how many answered, total adults and kids coming, how many declined.

02 The database — three tables, in plain English

Nothing fancier than three lists. Here's what each one is for, not just what columns it has.

Invites

one row per guest household you've invited

  • namewho they are
  • phonefor the WhatsApp link (not required)
  • tokentheir secret link code
  • statuspending → opened → submitted → edited
  • created_atwhen they were added

Responses

each guest's current answer — one row, gets overwritten

  • attendingyes or no
  • adult_countadults coming
  • kid_countkids coming
  • updated_atlast time they changed it

Response History

every answer ever given — nothing is ever erased here

  • attending / adult_count / kid_counta snapshot of one submission
  • submitted_atwhen that particular submission happened

Why keep both this and Responses? Responses answers "what did they say right now", this answers "what did they say over time" — e.g. seeing they first said 4 people, then changed it to 2.

flowchart TB
    Invite["One Invite\n(one guest household)"]
    Current["Their current answer"]
    Log["Their full answer history\n(every submission, kept forever)"]
    Invite -- "has at most one" --> Current
    Invite -- "has many entries in" --> Log

Deleting an invite deletes its answer and its history with it — nothing is left orphaned.

03 The invite lifecycle

Every invite moves through these states in one direction only — it never goes backwards.

pending→ opened→ submitted→ edited

pending — added, hasn't clicked their link yet · opened — clicked it, hasn't answered · submitted — answered once · edited — changed their answer at least once, and stays "edited" from then on even if they change it a third or fourth time.

04 Every function, and what it does

Every piece of logic in the app, grouped by who triggers it. Nothing here needs a login except the "Behind the login" group.

Guest-facing — no login required

Load my invite page
runs when a guest opens their link
Looks up the invite by its secret token, flips pending → opened (skipping known bot/preview visits), then shows the form — pre-filled if they've already answered.
Submit my RSVP
runs when the guest hits submit
Saves their answer as the current one, appends it to the permanent history log, and moves their status to submitted (or edited, if this isn't their first time).
Mark my link as opened
a small backup check on page load
A second, independent check that flips pending → opened — belt-and-suspenders in case the main page load didn't catch it.

Behind the login — admin only

See every guest
loading the Invitees tab
Lists every invite with its current answer attached, newest guest first.
Add a guest
submitting the "add invite" form
Creates a new invite with a fresh, unique secret link, starting at "pending".
Open one guest's detail
clicking into a guest
Pulls that one invite plus their current answer and their entire history, most recent submission first.
Delete a guest
clicking delete on a guest
Removes the invite — and, along with it, their current answer and their whole history. Permanent.
Bulk import
uploading a spreadsheet (.xlsx)
Reads every row, requires at least a name per row, and turns each valid row into a new guest in one go.
See the numbers
loading the Stats tab
Counts guests in each status, totals up adults/kids attending, and counts how many declined.

Security & plumbing — happen automatically

The checkpoint
before /admin pages ever load
Checks you're logged in before the page is even allowed to render; not logged in → bounced to the login screen.
The second check
on every single admin action, again
Each admin action independently re-checks you're logged in, even though the checkpoint above already did — so a request can't sneak past the front gate directly.
Log in
submitting the login form
Verifies your credentials and starts a session so the checkpoint above lets you through.
Sign out
clicking sign out
Ends the session — the checkpoint starts bouncing you to login again immediately.

05 What's actually running right now

Mock mode is on

  • No real database is connected yet — the credentials in the project are still placeholders.
  • Everything above is running against one made-up guest, sitting in the app's memory, not a real database — restarting the app resets it back to that one guest.
  • The admin login currently accepts literally any email and password — it's a stand-in so the dashboard is reachable for testing, not real security.
  • Nothing about how the screens work or how the data is shaped changes once a real database is connected — only the flip of one setting.

06 What's planned but not built yet

From the project's own scoping notes — things that don't exist in the app at all right now.

Not built yet

  • Editable wedding details — the couple's names, date, venue, and message wording are hardcoded in the code today; there's no admin screen to change them without a code change.
  • Editing an existing guest — you can add or delete a guest, but there's no way to fix a typo in their name or phone number yet.
  • One-tap WhatsApp send button — a planned button per guest that would open WhatsApp with their invite message pre-filled, so a human still taps "send" themselves. Doesn't exist yet.
  • Tracking who's been contacted — no record yet of how many times a guest has been messaged, or a flag for "tried 5 times, call them instead."
  • Day-of reminder prep — no screen yet to generate a venue/time reminder message for confirmed guests.
  • Post-wedding thank-you prep — same idea, for after the wedding — not built.
  • Bride/groom side & relation tags — no way yet to mark a guest as bride's side/groom's side, or family/friend/coworker.

One hard rule that is already locked in for all of the above: no message ever gets sent automatically or in bulk — every send stays a manual, human tap, to protect the couple's WhatsApp number from being flagged as spam.

07 Glossary — the confusing words, plainly

token
A long, hard-to-guess code built into each guest's personal link. It works like a password, except the guest never has to type one — having the exact link is proof enough.
upsert
"Update it if it already exists, otherwise create it." Used so a guest can submit their RSVP more than once without ending up with duplicate rows.
RLS / "deny all"
A rule set directly on the database saying "by default, nobody can read or write anything." The app deliberately locks every door and only opens them through its own secure server code — never directly from a browser.
service role key vs. public key
Two different database passwords the app can use. The public one can only do what's explicitly allowed (safe to expose). The other can do anything, and is only ever used in secure server-side code — never sent to a browser.
the checkpoint (proxy)
A guard that runs before a page is even allowed to load, used here to protect everything under the admin area.
mock mode
A stand-in for the real database — pretend data living only in memory, used so the app can be built and tested before a real database exists.
